# Peekd

Peekd is a lightweight, high-performance web file server written in Go for
browsing and sharing local files. It provides a clean directory interface,
previews for text, code, images, audio, and video, resumable downloads through
HTTP byte ranges, and direct file delivery that can use Go's `sendfile`
optimization with minimal user-space copying.

## Installation

### One-liner (Linux & macOS)

Download and install the pre-built binary from GitHub Releases:

```bash
curl -fsSL https://raw.githubusercontent.com/jiacai2050/peekd/main/install.sh | sh
```

The installer supports custom versions and installation directories:

```bash
curl -fsSL https://raw.githubusercontent.com/jiacai2050/peekd/main/install.sh | sh -s -- \
  --version v1.0.0 \
  --prefix "$HOME/.local/bin"
```

| Option | Description | Default |
| :--- | :--- | :--- |
| `--version`, `-v` | Release version to install | `latest` |
| `--prefix`, `-p` | Directory to install the binary | `~/.local/bin` |
| `--china` | Use a download proxy | `false` |

### Via Go Install

```bash
go install github.com/jiacai2050/peekd@latest
```

## Usage

Start the server for the current directory:

```bash
./peekd
```

By default, Peekd listens on `:8090`. Serve another directory with `-root`
and choose a custom listening address with `-addr`:

```bash
./peekd -root ~/Downloads -addr :9000
```

If the requested port is already in use, Peekd automatically tries the next
port.

Print the version and build information:

```bash
./peekd -version
```

You can also start it directly with Go:

```bash
go run . -root ~/Downloads
```

At startup, Peekd prints the local URLs that can be opened in a browser.
Directories have a custom listing sorted by modification time. Text files,
images, audio, and video have dedicated previews; other files are served
directly. Text previews are limited to 4 MiB; larger text files are served
directly instead. Use `-max-preview-size` to change the limit. It accepts
values such as `4M`, `512K`, or `4194304`. Requests from non-browser user
agents receive the original file instead of opening previews.

### Resumable downloads

Direct file responses use Go's `net/http` file-serving implementation. It
supports HTTP byte ranges, so interrupted downloads can be resumed with
`curl`:

```bash
curl -C - -O http://127.0.0.1:8090/large-file.iso
```

The same range support is used by download managers and browsers. You can
inspect the response headers with:

```bash
curl -I http://127.0.0.1:8090/large-file.iso
```

For a file that should always be returned in its original form, append
`raw=1`:

```bash
curl -o large-file.iso 'http://127.0.0.1:8090/large-file.iso?raw=1'
```

`raw=1` is also used internally by image, audio, and video previews. Go's
standard file server handles range requests and conditional requests for
direct file responses, while preview pages are generated by Peekd.

## When does Go use `sendfile`?

The key detail in Go's networking library is that `net.TCPConn` implements
the `io.ReaderFrom` interface. When a file is written to a TCP connection with
`io.Copy(conn, file)`, the execution flow is:

1. `io.Copy` checks whether the source implements `io.WriterTo`.
2. If not, it checks whether the destination implements `io.ReaderFrom`.
3. `net.TCPConn` implements `io.ReaderFrom`, so its optimized read path is
   selected.
4. On Linux, Go's internal implementation in
   `src/net/sendfile_linux.go` checks whether the source is a real disk file
   represented by `*os.File`.
5. If the conditions are met, Go automatically calls the
   `sys_sendfile` system call.

This allows the operating system to transfer file data from the file
descriptor to the socket without copying the contents through a user-space
buffer. `http.FileServer` and `http.ServeFile` can use the same optimized
file-copy path when their response is backed by a compatible network
connection.

The optimization still depends on the source being a regular `*os.File`, the
destination being a compatible network connection, the operating system
supporting it, and the response not requiring transformations such as
compression, templating, or encryption. It is an implementation optimization,
not a guarantee that every response will use `sendfile`.

In this project, non-text files are passed directly to `http.FileServer` and
can use this optimized path. Text files are read into memory and rendered
inside an HTML preview template, so they cannot use zero-copy file transfer.

## Verify `sendfile` on Linux

Build the server and start it under `strace`, tracing only the `sendfile`
system call:

```bash
go build -o peekd .
strace -f -e trace=sendfile ./peekd -root /path/to/files
```

In another terminal, request a regular binary file:

```bash
curl -o /dev/null http://127.0.0.1:8090/large-file.bin
```

If Go uses the Linux optimization, `strace` prints one or more calls similar
to this:

```text
sendfile(8, 7, NULL, 4194304) = 4194304
```

Use a regular non-text file for this test. Text files go through the preview
template and are read into memory, so they intentionally do not use
`sendfile`. If no `sendfile` call appears, check that the file is served
directly, the request is not being transformed by middleware, and the
connection is not using an unsupported transport such as TLS.
